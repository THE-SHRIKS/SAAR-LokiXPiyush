# SAAR — Financial Correctness Results

All data here is synthetic. Provenance: generated by `tests/fixtures/corpus/make_corpus.py` and
`tests/fixtures/golden/*.py`. No real customer or third-party documents.

## Method

A deterministic generator produces two independent workspaces (different seeds, vendors, currency
mixes and outcomes) and a **ground-truth ledger** (`ledger.json`) computed in integer minor units by
the generator, never by SAAR. The harness (`src-tauri/src/integration_tests/corpus.rs`) ingests every
file through the production ingestion path (PDF text layer, RapidOCR for images, CSV mapper), then
runs the production reconciliation and anomaly code and compares each result with the ledger.

| Workspace | Invoices (PDF) | Receipts (scanned PNG) | Bank rows | Currencies |
|---|---|---|---|---|
| alpha | 32 (6 two-page) | 6 (good, fair, poor) | 167 | USD, EUR, INR |
| beta | 15 (2 two-page) | 4 | 72 | USD, INR |

The corpus uses three invoice layouts, US/European/Indian number formats (`1,234.56`, `1.234,56`,
`1,23,456.00`), `yyyy-mm-dd` and `dd.mm.yyyy` dates, discounts, per-invoice tax rates, a missing
date, a deliberately wrong printed total, a re-sent copy, a reused invoice number, partial
payments, short payments, double payments, recurring charges, refunds, and one unexplained debit.

## Defects the corpus exposed, and their fixes

The first run produced **40 mismatches**. Root causes and fixes:

| Defect | Evidence | Fix |
|---|---|---|
| Amount parser stripped every comma, so `2.306,22` became 2.30 and `856,80` became 85,680.00 | totals 230 vs 230,622; 8,568,000 vs 85,680 | Decimal separator inferred from the number's shape; grouping validated; excess precision rejected, not truncated |
| Text without digits parsed as 0 (after the first fix) | caught by the malformed-row test | Only a blank cell is 0; other text is an error |
| CSV Debit/Credit parse failure became 0; rows with a bad or missing date were skipped | malformed-row test imported 3 rows from a file with a bad row | Row errors carry the row number; only blank lines and summary rows are skipped; debit and credit on one row is rejected |
| Invoice number and date recognised only for three English labels | layouts B and C: number and date never extracted | Pattern-based labels (Reference, Rechnung / Invoice, Issued, Datum, Due, Faellig); `dd.mm.yyyy` |
| Discount not part of the arithmetic check | valid discounted invoices flagged as inconsistent | `subtotal - discount + tax = total` |
| Currency detected by substring, so a name containing `EUR` read as EUR | code review | Whole-word ISO code, most frequent wins |
| Receipt totals read as 0 | `TOTAL` and `USD 128.45` arrive as separate OCR lines; a rotated scan read the value first | Amount token parsing, next-line and previous-line fallback; unreadable total flagged for review |
| Invoice with no date never matched its payment | 2 payments with no link | Match on amount plus invoice-number token; type `EXACT_NO_DATE`, confidence 0.9, explanation states the date is missing |
| Identical invoices took each other's payments | invoice and its re-sent copy were crossed | Invoice number as a whole token, matched first; `…-0002` is not found inside `…-0002-R` |
| Chat totals derived from the latest 50 rows | code review | Totals from a full SQL aggregate |
| Two distinct debits of one amount to one merchant never flagged | code review | `POTENTIAL_DUPLICATE_PAYMENT` rule; monthly cycles excluded |
| Other-currency rows disappeared from summaries | code review | Summary reports excluded currencies with counts and gross amounts |

## Dynamic-result tests (`integration_tests/dynamic.rs`)

- Two workspaces each equal their own ledger, and their results differ.
- The same rows in reverse order give identical totals.
- Adding a 1,234.56 debit raises expenses by exactly 123,456; adding a 200.00 credit raises income by exactly 20,000.
- Summing stored rows in pages of 25 equals the full aggregate.
- Correcting a transaction description is reflected afterwards and is audited.

## Full regression

Rust: 97 library tests (including the corpus and dynamic tests), p1 through p6, migration (3), golden dataset (2), all passing. Frontend: type-check clean, 7 tests passing.

## Known weaknesses (not fixed)

1. **Chat answers are not yet deterministic.** The language model still writes the figures. Wrong figures can still appear and can be labelled "grounded". This is the largest open correctness gap.
2. **Currency conversion is not implemented.** Other currencies are reported as excluded from base-currency totals; none are converted.
3. **Anomaly noise.** `LARGE_UNMATCHED` fires on every large recurring payment (alpha produces 59 anomalies, many of them monthly rent). It is accurate but not useful.
4. **Partial payments** are not linked to their invoice; they are only prevented from being mislabelled as exact matches.
5. **Corpus scope.** Invoices are generated with PyMuPDF text layers; the scans are rendered text with blur, noise and rotation. Real-world scans, handwriting, stamps and photographs are not covered.
6. **Matcher date rule.** A mismatched year or day/month swap in a printed date is not detected.
